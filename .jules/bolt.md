## 2026-09-18 - Labels Are Normalized on the Way Out of the Store, Not Just on the Way In

**Learning:** `internal/scheduler`'s `Matches`/`Score`/`Eligible` each call `store.NormalizeLabels` on both the pool's and the job's `Labels` before comparing them, and `bestPool` calls all three per (job, pool) pair in `assign`'s loop over every queued job -- run on every reconcile tick. But `store.Pool.Labels` and `store.Job.Labels` are already normalized once when the store loads them (`queries_fleet.go:274,346`, `queries_events.go:68,146`), so the scheduler's hot path was re-deriving a value (dedupe map + `slices.Sort`) that was already correct on essentially every call. This wasn't visible as a classic N+1 or a loop-local allocation -- it looked like ordinary, already-pure label comparison code -- because the redundancy was between the *loader* and a *far-away caller*, not within one function.
**Action:** Before adding caching or restructuring a hot-path comparison function, check whether its input already satisfies the invariant the function establishes (sorted/deduped/normalized) by the time it's typically called -- grep the type's field for where it's assigned, not just where the "normalizing" function is called. When the invariant usually already holds, add an allocation-free `isXxx` fast-path check (no map, no sort) that returns the input unchanged, and fall back to the real work otherwise; this keeps the function correct for genuinely unnormalized input while eliminating the allocation and O(n log n) sort for the common case. Measured on `NormalizeLabels` with a 4-label already-normalized slice: 221.4 ns/op, 64 B/op, 1 alloc/op -> 61.71 ns/op, 0 B/op, 0 allocs/op (~3.6x, allocations eliminated).
