# The marketplace deployment package

What a VPS provider needs to offer Zoomies as a one-click deployment, and what
an operator can run by hand to get the same result.

It deploys **a controller**. Zoomies is self-hosted and
bring-your-own-infrastructure: this puts the always-on half on one instance, and
the runner capacity stays yours. The default install also runs an agent on that
instance, so it can execute jobs from the first minute; set `ZOOMIES_MODE` to
`controller` when the runners live elsewhere.

## The files

| File | What it is |
| --- | --- |
| `release.env` | The release this package installs: the controller image by tag and digest, the installer and its checksum, and the version a joining agent is given. Hand-edited when a new release becomes the baseline. |
| `images.lock` | Every image that release publishes, and the digest each tag resolved to. Generated by `make marketplace-lock`. |
| `inputs.env.example` | The settings that differ between one customer and the next. Copy it, fill it in. |
| `answers.yaml.tmpl` | The answers `zoomies init` is given, with the instance's own values still to substitute. |
| `bootstrap.sh` | First boot: install a container runtime, render the answers, run the pinned installer, wait for health, leave a note. |
| `cloud-init.yaml.tmpl` | The cloud-config the three files above are rendered into. |
| `render.sh` | Does the rendering. |

## Using it

```sh
cp inputs.env.example inputs.env
$EDITOR inputs.env                 # at minimum, the hostname
./render.sh inputs.env > cloud-init.yaml
```

Boot an Ubuntu 24.04 LTS instance with `cloud-init.yaml` as its user data. When
it comes up, `/etc/zoomies/first-login.txt` says how to finish: read the setup
token from the controller's log, create the first administrator in the browser,
connect GitHub, make a pool.

## What it will not do

**It carries no secret.** Not the GitHub App's private key, not the webhook
secret, not an administrator password, not a join token. Everything a provider's
form collects becomes instance metadata, which is readable by anything on the
instance that can reach the metadata service, kept in the provider's own
database, and printed in cloud-init's log — and a credential that has been
copied to all three places cannot be rotated out of them. `render.sh` refuses an
inputs file that sets one.

So the parts that need a credential happen afterwards, in the browser, over the
connection the operator already trusts. The first administrator is created with
the setup token the controller prints while no account exists; GitHub is
connected from the UI by an administrator who is already signed in.

**It does not terminate TLS.** This slice publishes plain HTTP for a proxy or
load balancer in front of it, and refuses any other `ZOOMIES_TLS` by name rather
than quietly serving an origin in the clear.

**It has not been tested on a provider yet.** The implementation is complete and
its rendering is checked by tests in `internal/docs`; a pristine-VPS run, the
first-workflow journey and a pilot review are separate work and are not claimed
here.
