# Zoomies UI audit: the signed-in pages

Audited at commit `0730e77b`, 29 October 2026. This is the follow-up to
[the first UI audit](archive/ui-audit-2026-10-01.md), which was about the route
into the product; this one starts where that one stopped, at the pages an
operator sees once they are signed in.

A review of every page an operator sees after signing in: inconsistencies,
missing hover affordances, data points that should be links, and sections that
earn less than the room they take. Nothing in the product was changed, so this
file is the finding list.

## How this was checked

* Built the real binary (`npm run build`, then `make build-nogui`) and ran
  `zoomies controller` with `ZOOMIES_SEED_DEMO=true` and
  `ZOOMIES_DISABLE_AUTH=true`, so every page was the shipped UI against the
  fixture fleet the Playwright suite and `zoomies demo` use.
* Photographed every signed-in route at 1440x900 and 375x812 in Chromium, and
  read the DOM at the same time: header widths, first-row positions, the tooltip
  that appears (or does not) on hover, and the bounds of the floating assistant
  button against the content under it.
* Routes covered: `/`, `/pools`, `/pools/:id`, `/runners`, `/runners/:id`,
  `/queue`, `/workflows`, `/jobs`, `/usage`, `/hosts`, `/hosts/:id`,
  `/providers`, `/providers/:id`, `/machines/:id`, `/installations`,
  `/repairs`, `/migrate`, `/kennel`, `/kennel/ai-context`, `/audit`,
  `/settings` and its twelve pages.
* Default visual style (Mission Control, dark). The design tokens are shared,
  so nothing here is a dark-mode-only artefact.
* Out of scope: the sign-in and first-run pages, the public `/status` page, and
  the two demo-only bands ("Zoomies demo system" and the "Authentication
  disabled" account label). Those say true things about a demo instance and
  nothing about a fleet.

## What is already good, so the rest is read in proportion

The foundations are strong and none of the findings below asks for them to be
redone: one token file, one status vocabulary, one data grid with real
keyboard, selection, sorting, column layout and empty states, a persistent
navigation with discoverable `g` chords, a command palette, and error copy
written for a person. The problems are almost all in what sits *above* the
records, and in the small number of places where a value that has a destination
was left as text.

## The findings by theme

| Theme | Findings |
| --- | --- |
| Density: chrome before records | C2, H7, N5 |
| Unreadable or unlabelled data | C1, N3, N4 |
| Missing quick links | C4, H1, H2, H3 |
| Duplicated information | H4, H5, H6, N1, N2, N6, N7 |
| Overlap and clipping | C3, N3, N12 |
| Absent values given equal billing | N8, N11 |
| Controls that read as something else | N9, N10 |

# 1. Critical

## C1. A grid's column headers are two or three characters wide and say nothing on hover

* **Pass**: Designer
* **Where**: `web/src/lib/components/DataGrid.svelte` (the `thead` render and
  the `.heading-label` block, around lines 1075 to 1135), reached from
  `/pools`, `/jobs`, `/workflows`, `/runners` and `/queue` at 1440px. Audit,
  which has five wide columns, is the one grid the problem does not reach.
* **Problem**: at 1440 the header row of the Pools grid reads
  `NAME | R… | LA… | T… | B… | P… | RUNNERS | … | I… | LIF… | DO… | S… | AC…`,
  and Jobs reads
  `JOB | REP… | STATE | QU… | DU… | FAILE… | WO… | LABE… | POOL | RUNN… | QUEU… | R…`.
  Measured widths: 78px for `LABELS`, `TARGET`, `BACKEND`, `PLATFORM`,
  `IDLE TIMEOUT`, `LIFETIME`, `DOCKER` and `STATUS` on Pools, and 97px for most
  columns on Jobs. About 30px of each of those is the drag grip the grid puts
  before every label. The full label exists in the cell's text and in the
  accessibility tree, but hovering a truncated header produces no bubble unless
  that column happens to declare `help` (`LIFETIME` does, which is why only that
  one is dotted). A sighted operator cannot name the columns of the table they
  are reading, and cannot choose a sort they cannot describe.
* **Fix**: three small changes, in this order.
  1. Wrap the heading label in the shared tooltip unconditionally:
     `<Tooltip bare text={column.help ?? column.header} placement="bottom">`
     around the `<span class="heading-label">` branch, so the help text wins
     where there is one and the label is the fallback. This alone fixes the
     complaint for a mouse.
  2. Reclaim the grip's width: show `.move` on `th:hover`, `th:focus-within`
     and while dragging, and add `padding-left: 0` to `.heading` otherwise.
     `LIFETIME` then fits.
  3. Below about 1280px, hide `priority: 'wide'` columns rather than squeeze
     them. The grid already knows (`narrowDesktop`), and the Columns chooser
     already explains a hidden-by-width column, so this is a rule change, not a
     new concept.

## C2. On the pages an operator lives in, the first record is below the fold at 1440x900

* **Pass**: Designer
* **Where**: `/runners`, `/queue`, `/hosts` and `/usage` at 1440x900.
* **Problem**: measured top of the first data row, with a 900px window: Pools
  684, Jobs 689, Workflows 689, **Queue 857**, **Runners 937**, **Hosts 1061**.
  `/usage` has no record in the first screen at all. The band alone is 298px
  tall on Runners and Queue. Everything above the records is individually
  defensible and collectively fatal: eyebrow, title, subtitle, a summary line,
  the band, a "Fleet context" heading, two disclosure rows, a search box, three
  filter selects, and a switch with a two-line explanation. An operator who
  opens Runners to see what is running sees no runner.
* **Fix**: the band already has a size the operator can choose, and `slim` is
  the one default nothing uses (`web/src/lib/bands/pages.ts`,
  `defaultBandSize`). Make `slim` the default for the working pages (Runners,
  Pools, Queue, Jobs, Workflows, Hosts) and keep `standard` for the Overview.
  Then move the "Include removed" paragraph on Runners
  (`web/src/routes/Runners.svelte`) into the switch's tooltip, and merge the two
  disclosures ("How runners move through their states" and "Explore fleet
  activity over the last 24 hours") into one row, since both open reference
  material and neither is a decision.

## C3. The floating assistant button covers page content, including a primary action

* **Pass**: Designer and First-time user
* **Where**: `web/src/lib/assistant/EliWidget.svelte` (`.fab` is
  `position: fixed; right: var(--z-space-5); bottom: var(--z-space-10)`), seen on
  `/migrate` at 1440, `/` at 1440 and `/hosts` at 375.
* **Problem**: the button is 56x56 at (1364, 804) to (1420, 860) in a 1440x900
  window, and nothing reserves that corner. On `/migrate` the wizard's **Next**
  button is at (1358, 841) to (1416, 873), so the assistant covers its upper
  right and the label reads "Nex" with a paw on it. On the Overview it covers
  the last 52px of the footnote "Trends, waits and outcomes cover the last
  hour.", which is the sentence that says what the four tiles above it count. At
  375 it sits on the metric tiles. A control that hides another control is the
  one kind of overlap a user cannot work around.
* **Fix**: reserve the corner. Add
  `padding-bottom: calc(var(--z-space-12) + var(--z-safe-bottom))` to `.page` in
  `App.svelte`, and make fixed or sticky footers (the wizard bar on `/migrate`,
  `PoolActionBar`, the drawer footers) end their primary action at
  `right: calc(var(--z-space-12) + var(--z-space-3))`, so the last 88px of the
  bottom-right is a lane nothing occupies. A cheaper alternative, if the layout
  churn is unwelcome: give `EliWidget` a collision check on route change and
  offset it above whatever it finds within 24px. The first is the one that
  cannot regress.

## C4. A host's name links to the list of hosts, not to that host

* **Pass**: First-time user
* **Where**: `web/src/lib/runners/RunnerFacts.svelte:41`,
  `web/src/routes/RunnerDetail.svelte:245`,
  `web/src/routes/MachineDetail.svelte:224`. All three write `href="/hosts"`, and
  all three have `host_id` in scope. Routes: `/runners/:id`, `/machines/:id`.
* **Problem**: `/hosts/:id` exists, is linked from every host card, and is the
  page that answers "is this host healthy, is it cordoned, has it room". The
  runner page shows the host's *name* as a link, so the operator clicks it
  expecting that page and lands on a list of every host with no indication which
  one they came for. The pool link immediately beside it does the right thing
  (`/pools/{pool_id}`), which makes the host one read as a bug rather than a
  decision.
* **Fix**: `href={runner.host_id ? \`/hosts/${runner.host_id}\` : '/hosts'}` in
  all three places, matching the pool link and the host card's own
  `href="/hosts/{host.id}"`. MachineDetail's breadcrumb already does this
  correctly, so it is a two-line change there.

# 2. High impact

## H1. The figures that beg for a drill-down are the ones that are not links

* **Pass**: First-time user
* **Where**: `web/src/lib/hosts/HostCard.svelte` ("4 of 6 slots in use · 2
  free"), `web/src/routes/Pools.svelte` (`runnersCell`: "3 of 8 busy · 38%"),
  `web/src/routes/Workflows.svelte` (the `repo`, `workflow` and `jobs` columns
  are declared with `value` and no `cell`, so they render as text), `/runners`,
  `/jobs`.
* **Problem**: the destinations already exist and are already filterable, which
  I verified against the fixture fleet: `/runners?host_id=host_demoa` returns 4
  runners, `/runners?pool_id=pool_demolinux` returns 8,
  `/jobs?repo=acme%2Fapi` returns 18 with a "Repository · 1" chip, and
  `/jobs?pool_id=pool_demolinux` returns 48. So the operator reading "3 of 8
  busy" on a pool row has to memorise the pool, open Runners, and set the Pool
  select themselves. The row actions are inconsistent with this too: the Pools
  row opens the pool, the Jobs row opens a drawer, and the number inside the
  Pools row goes nowhere.
* **Fix**: link the figure, not the whole cell, and stop propagation so the row
  keeps its own click (the pattern is already written in
  `web/src/routes/Jobs.svelte`, `poolCell`):
  * Host card: the "n of m slots in use" text becomes
    `<a href={`/runners?host_id=${host.id}`}>`, tooltip "Runners on this host".
  * Pools `runnersCell`: the "n of m busy" text becomes
    `<a href={`/runners?pool_id=${pool.id}`}>`.
  * Workflows: give `repo` and `jobs` a `cell` that links to
    `/jobs?repo=<encoded repo>` and `/jobs?workflow=<workflow>`.
  * Machine detail: "Provider" in the facts list is plain text while the
    breadcrumb above it links, so make the row
    `<a href={`/providers/${m.provider_id}`}>` too.

## H2. Two of the Overview's four tiles land without the filter the number came from

* **Pass**: First-time user
* **Where**: `web/src/lib/overview/FleetMetrics.svelte:277` (`href="/runners"`)
  and `:288` (`href="/jobs"`).
* **Problem**: "Queued jobs" and "Running jobs" link to the filtered Jobs view,
  so the pattern is established. "Live runners 9" then opens every runner the
  controller ever knew, including removed ones, which is a superset and reads as
  a contradiction. "Median queue wait 19s" opens all jobs of all states over all
  time, where the figure cannot be found at all: a queue wait is only measured
  on jobs that finished.
* **Fix**: point the live tile at
  `/runners?state=provisioning&state=registering&state=idle&state=busy` (the
  Runners page accepts a `state` list) and the wait tile at
  `/jobs?state=completed&since=<the same hour the sparkline covers>`, reusing
  the hour boundary the series already computes. If a filtered landing is
  genuinely not wanted, drop the `href` instead of pointing at the wrong page: a
  tile that is not a link is honest, one that lands on a page without the number
  is not.

## H3. `/pools?installation=<id>` is a link that does not filter

* **Pass**: First-time user
* **Where**: `web/src/lib/installations/InstallationCard.svelte` (the Pools fact
  writes `<a href="/pools?installation={installation.id}">`), against
  `web/src/routes/Pools.svelte`, which reads only `q` and `status` from the
  address.
* **Problem**: opening `/pools?installation=ins_demoacme` returns both demo
  pools and shows no chip, so the address does nothing. On a controller with two
  GitHub connections, "2 pools" under `acme` and "5 pools" under another
  organisation both open the same list of seven, and the operator has to trust
  the search box to narrow it. A link that silently widens the question is worse
  than no link.
* **Fix**: either honour the parameter (add `installation` to what the Pools
  page reads, filter `pool.installation_target` against it, and show a chip), or
  point the link at `/pools?q=<the installation target>`, which the page's
  search already matches against name, label or target today. The second is a
  one-line change and cannot drift.

## H4. The same summary is said three times on one screen

* **Pass**: Designer
* **Where**: `/hosts`, `/jobs`, `/workflows`, `/providers` at 1440.
* **Problem**:
  * Hosts says it three ways within 400px: the header summary ("3 hosts · 3
    connected · 9 of 12 runner slots in use · 1 via Tailcat"), the band ("3 hosts
    are connected. 9 of 12 slots in use. Every host has checked in."), and six
    tiles whose first two are "Hosts connected 3/3" and "Runner slots in use
    9/12".
  * Jobs and Workflows say it twice within 40px: the band ("3 jobs are running.
    6 waiting for a runner. 1 failed and 0 succeeded in the last hour.") and the
    chip row directly under it ("Running 3", "Queued 6", "Failed 1").
  * Providers says it twice: the band ("2 machines are owned. Up to 4 at once.
    Nothing needs review.") and four tiles ("Machines owned 2", "Ceiling 4",
    "Needing review 0", "Paused providers 0").
* **Fix**: one summary per page, and the band wins because it carries a sentence
  an operator can read. Drop the `summary` snippet from Hosts
  (`web/src/routes/Hosts.svelte`, the `PageHeader` `meta`), drop the four tiles
  on Providers (their two non-duplicated figures can join the band's stat strip,
  which is the mechanism `PageBand` already has), and let the Jobs chip row keep
  the counts while the band keeps the sentence without repeating the numbers.

## H5. Every detail page carries two breadcrumbs, an eyebrow and a heading

* **Pass**: Designer
* **Where**: `web/src/lib/shell/TopBar.svelte` (the `crumb` derived from the
  current section) together with `PageHeader`'s `breadcrumb` prop, on
  `/hosts/:id`, `/runners/:id`, `/providers/:id`, `/machines/:id`.
* **Problem**: a host page opens with "Hosts › demo-builder-1 · Host health" in
  the top bar, then "Hosts › demo-builder-1" in the page, then
  "INFRASTRUCTURE", then "demo-builder-1". The host's name appears four times
  before any fact about it. On a phone the top bar's copy of the crumb is the
  one that has to truncate ("Settings › App…"), so the doubled pair costs most
  exactly where room is scarcest.
* **Fix**: pick one. The page's own breadcrumb is the better survivor (it
  contains the link to the section and is not competing with the connection dot,
  the bell, the search and the account menu for width), so let `TopBar` show
  only `router.title` and stop deriving `crumb` for routes that render a
  `PageHeader` breadcrumb. That also removes the truncation in N12.

## H6. Explanations standing where an action belongs

* **Pass**: First-time user
* **Where and problem**, all at 1440:
  * `/kennel`: the band says "Kennel Club is off. Turn it on to check the
    repositories this fleet serves." and offers no control to do it. Under it, a
    panel spends roughly 600px on "What it reads" and "What it never does"
    bullet lists. The switch that resolves the whole page is in the left rail,
    outside the reading line.
  * `/repairs` with nothing to repair: the band, three tabs that all read zero
    ("Needs you 0", "In progress 0"), a sign-in banner, and a History disclosure
    that starts open and contains an empty state. Two empty states and three
    zeros for one fact.
  * `/kennel/ai-context`: the four counts appear as figures ("Repositories 0,
    In setup 0, Ready 0, Needs attention 0") and beside them as filter chips
    ("All 0, In setup 0, Ready 0, Needs attention 0").
  * `/providers/:id`: "renting is switched off for this controller
    (provider.enabled), so no machine is created from any provider; nothing is
    drained, deleted or checked either" appears twice on one screen, once as a
    banner and once inside the Test machine panel.
* **Fix**: Kennel: put the switch in the band's `actions` snippet (the slot
  `FleetStatus` uses for Review), or make the off state one line plus the switch
  and move the two bullet lists behind a "What Kennel Club reads" disclosure.
  Repairs: when all three counts are zero, render no tabs at all and one empty
  state. AI Context: keep the chips (they filter) and drop the figures, or the
  reverse, but not both. Provider detail: keep the banner, remove the repeated
  sentence from the panel and let the disabled button's `reason` carry it.

## H7. On a phone, every list page opens on chrome instead of on a record

* **Pass**: Designer and First-time user
* **Where**: `/jobs`, `/pools`, `/queue`, `/workflows`, `/runners` and `/hosts`
  at 375x812.
* **Problem**: measured top of the first record at 375: Jobs 748, Pools 787,
  Workflows 804, Queue 868, Runners 1233, Hosts 1855. With the top bar and the
  bottom navigation, a phone's usable height is about 690px, so nothing shows a
  record on its first screen and Hosts needs more than two screens before its
  first host. What fills the space: the status chips wrap onto three rows
  (Jobs), the "Workflow runs | Every job" segmented control, the search box, the
  "Filters (0)" button, the "Cards | Rows" selector, the "Columns" button, and a
  strip of column labels.
* **Fix**: on a phone, put the chips in one horizontally scrolling row, drop the
  `Cards | Rows` segmented control into the Columns panel (it is a layout choice
  of the same kind), and show `Filters (n)` before the search rather than after
  it. Default a phone to the Cards view so the fold contains the first record,
  and let the column chooser be the place a Rows reader turns columns on.

## N8. Three absent values sit in the primary facts list

* **Pass**: Designer. **Where**: `web/src/lib/runners/RunnerFacts.svelte`

  version" reading "Unknown"), `/runners/:id` at 1440. **Problem**: three of the

## N9. The band's size control reads as window buttons

* **Pass**: Designer. **Where**: `web/src/lib/bands/PageBand.svelte` (the
  `.tools` cluster: minus, wide rectangle, square, tall rectangle, cross), top
  right of every band. **Problem**: the shapes say minimise, maximise, restore
  and close, which is the one vocabulary every desktop user already has, and the
  first three are not that. The `−` looks like it will hide the band (it
  shortens it) and the `×` beside it genuinely does hide it, which makes the
  misreading plausible rather than harmless. **Fix**: replace the three size
  glyphs with one control that names the current size ("Standard") and opens a
  `Segmented` of the four, or keep the four and give the group a word on hover
  (`Size: Slim`), so the cluster reads as a scale and not as window chrome.

## N10. Audit's filters are a full-width column where every other list page's are a row

* **Pass**: Designer. **Where**: `web/src/routes/Audit.svelte` (its `FilterBar`

  1440. **Problem**: five stacked rows, about 170px, where Jobs and Queue fit
  eight controls into one row. The same component in two shapes for the same
  job. **Fix**: let the filter bar wrap as its siblings do (a `flex-wrap` row
  with a minimum search width), which also recovers the vertical space that
  makes Audit the one list page that does show records above the fold.

## N11. The Usage band's figures wrap one tile onto a second row

* **Pass**: Designer. **Where**: `web/src/lib/bands/BandStats.svelte` via
  `web/src/routes/Usage.svelte`, `/usage` at 1440. **Problem**: six figures fit
  five to a row, so "Runner busy share 9.8%" stands alone under the other five.
  The band is 374px, the tallest on any page, and its shape changes with the
  window width. **Fix**: five figures in the strip and the sixth in the sentence
  ("62% succeeded, 9.8% of runner time busy"), or a two row strip designed as
  two rows.

## N12. A phone's top bar loses the section it is in

* **Pass**: First-time user. **Where**: `web/src/lib/shell/TopBar.svelte` (the
  `.page` and `.crumb` rules), at 375 on `/settings/appearance`
  ("Settings › App…") and `/jobs` ("Workflows › J…"). **Problem**: the only
  place the bar answers "where am I" truncates the page name, because the
  connection dot, the bell, the search and the account button have already taken
  the width. **Fix**: removed by H5 (one breadcrumb); if H5 is not taken, hide
  the crumb below 480px instead of truncating it, and give the title
  `min-width: 0` plus its full text in a tooltip.

# The first-time walkthrough, in the order a new operator meets it

1. **Overview.** The band answers the first question ("11 things need you") and
   offers the way in, which is the strongest moment on the product. Then the
   same 11 is in the top bar's bell, and the failures banner adds a second,
   differently-shaped count. I hesitated on which of the three was the real
   list; they lead to the same drawer, so the hesitation is free but real.
2. **"Live" under the title.** I read it as a second, different status from the
   dot in the top bar and spent a moment working out that it was not.
3. **Runners.** I could not see a runner. I scrolled past a band, a context
   heading and two disclosures, and by then I had stopped reading and started
   scrolling, which is the failure mode this page has to avoid.
4. **Following one runner.** On the runner page I tried to open the host it was
   on, because "is the host healthy" is my next question, and landed on the
   Hosts list. From there I found the host and its card, then wanted the runners
   on it, and found no link back to the list I had come from. The round trip
   exists; it is just not paved.
5. **Jobs.** The chip row and the band tell me the same six numbers. The table
   headers read `REP…`, `QU…`, `FAILE…`, so I read the cells and guessed the
   columns. The pool and runner cells both truncate to `zoomle…`, and they have
   tooltips, so a hover is required to tell one column from the other.
6. **Hosts.** Six tiles, a Machines panel with a seven stage pipeline, then the
   cards. I understood the fleet before I saw a host, which is the right order
   for a status page and the wrong one for a page called Hosts.
7. **Settings.** The rail plus the global sidebar plus, on Configuration, an
   "On this page" list makes four columns of navigation around one column of
   content. It never confused me, and it did make the content column narrow
   enough that each setting's description wrapped to five lines.
8. **Kennel Club.** I was told it was off and asked to turn it on, in a sentence
   with no button, above 600px of explanation. This was the only place I stopped
   and considered leaving the page.

# What I would not change

* The band's existence, or its voice. It is the best thing on the product; the
  finding is about its default height on working pages, not its idea.
* The grid's feature set (selection, bulk actions, column layout with a
  remembered per-grid choice, keyboard, empty and error states). The findings
  are about header legibility and where the toolbar sits on a phone.
* The status vocabulary, the tokens, and the copy that explains a refusal. All
  three are consistently better than the market norm and are what make the
  denser parts of the UI worth fixing rather than deleting.

# If only three things are done

C1 (headers readable on hover) is a few lines and repairs every list page. C4
(host links) is three lines and repairs a broken promise. H1 (the numbers that
should be links) is the change an operator would notice most, because it turns
four dead figures into four answers.
